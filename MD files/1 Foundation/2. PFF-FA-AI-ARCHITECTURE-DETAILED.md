The platform must provide a reusable AI runtime capable of supporting multiple PFF-FA business workflows through a common architecture.

# 3. Architectural Principles

## 3.1 Enterprise Authority

Enterprise systems remain authoritative for operational and business decisions.

The AI platform consumes those decisions.

---

## 3.2 AI Orchestration

AI is responsible for interpreting user intent, selecting workflow capabilities, assembling context, coordinating controlled tools and producing a grounded conversational response.

---

## 3.3 Deterministic Control

Security, authorization enforcement, batching, retry, timeout, idempotency, schema validation, transaction protection and other critical controls must be deterministic wherever practical.

The SLM must not be the only enforcement mechanism.

---

## 3.4 Controlled Tool Access

The SLM never receives unrestricted API or database access.

All enterprise operations pass through governed tools.

---

## 3.5 Context Before Reasoning

The SLM should reason over relevant, authoritative and bounded context rather than receiving uncontrolled enterprise datasets.

ERC is the primary operational context mechanism.

---

## 3.6 Knowledge vs Operational Truth

RAG provides knowledge.

Enterprise APIs/events provide operational truth.

These sources must remain distinguishable.

---

## 3.7 Workflow-Level Agents

Agents represent meaningful business capabilities/workflows.

Enterprise microservices do not automatically become individual agents.

---

## 3.8 Durable Execution

The platform must support workflows that span multiple HTTP requests, external portal actions, human decisions and asynchronous events.

---

## 3.9 Evaluation as Engineering

AI quality must be continuously evaluated.

A technically successful request is not necessarily an AI-quality-successful request.

# 13. Execution Pattern

The platform supports:

## Sequential

```text
A → B → C
```

Use when B depends on A.

## Parallel

```text
      ┌→ B
A ────┼→ C
      └→ D
```

Use when B, C and D are independent.

## Fan-out / Fan-in

```text
          ┌→ Batch 1 ─┐

          ├→ Batch 3 ─┤
          └→ Batch N ─┘
```

# 16. ERC Batch Strategy

Initial batch size:

**20 records**

Example:

```text
Teams = 103

Batch 1 = 1–20
Batch 2 = 21–40
Batch 3 = 41–60
Batch 4 = 61–80
Batch 5 = 81–100
Batch 6 = 101–103
```

Officials follow the same model.

The batch size must remain configurable.

The production value must be determined through evaluation and load testing rather than hardcoded assumptions.

# 24. Memory Architecture

Memory is separated into:

### Conversation Memory

User conversation history.

### Session State

Session lifecycle and identity references.

### Workflow State

Durable AI workflow execution state.

### ERC Memory

Previously assembled context where safe to reuse.

### Cache

Reusable results with explicit TTL and invalidation.

### Model KV Cache

Inference optimization.

These are separate concepts and must not be implemented as one generic "memory" store.

# 48. Architectural Anti-Patterns

The implementation must avoid:

## One microservice per agent

Unless independent deployment/scaling is justified.

## One LLM prompt containing all enterprise data

Use ERC and context selection.

## LLM as business-rule engine

Never.

## Direct database access

Never.

## RAG as operational database

Never.

## SLM-controlled authorization

Never.

## SLM-generated URLs

Never.

## Blind transaction retry

Never.

## In-memory-only long-running workflows

Never.

## Unversioned prompts

Never.

## AI evaluation only after production

Never.

## Logging raw sensitive context

Avoid and apply mandatory redaction.

```text
    ↓
LangGraph
    ↓
Tools
    ↓
ERC Mapping
    ↓
RAG Mapping
    ↓
Evaluation Dataset
    ↓
Observability
```

The core platform should not require redesign for each new workflow.

# 52. Architecture Governance

- System boundaries
- Data ownership
- Agent architecture
- LangGraph architecture
- ERC
- SLM
- Security
- Tool/MCP
- Eventing
- State
- AI evaluation
- Deployment boundaries

must be reviewed through the agreed architecture governance process.
