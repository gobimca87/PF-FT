# PF-FT Enterprise Agentic AI Platform — State Model

**Document ID:** PF-FT-AI-STATE-MODEL  
**Version:** 1.0.0  
**Status:** Development Baseline  
**Platform:** PF-FT Enterprise Agentic AI Platform / Adam AI  
**Runtime:** Python / FastAPI / LangGraph  
**Primary State Concept:** Durable, versioned AI execution state  

---

# 1. Purpose

This document defines the state model for the PF-FT Enterprise Agentic AI Platform.

The platform contains multiple kinds of state that must remain separate:

- Request state
- Conversation state
- Session state
- Supervisor state
- Agent state
- LangGraph execution state
- Workflow state
- ERC state
- Tool execution state
- RAG state
- SLM execution state
- Human-in-the-loop state
- External-event waiting state
- Cache state
- Error/recovery state

The primary objective is to ensure that state is:

- Explicit
- Durable
- Recoverable
- Versioned
- Observable
- Secure
- Consistent
- Resumable
- Independent from enterprise authoritative state

---

# 2. Core State Principle

> **AI state describes what the AI platform is doing; enterprise state describes what the business system has decided or executed.**

The AI platform must never confuse derived AI state with authoritative enterprise business state.

```text
Enterprise State
      │
      │ authoritative
      ▼
AI Platform
      │
      ├── Conversation State
      ├── Session State
      ├── Workflow State
      ├── Graph State
      ├── ERC
      └── Runtime State
```

---

# 3. State Hierarchy

The runtime uses the following hierarchy:

```text
Platform
  │
  └── Conversation
        │
        └── Session
              │
              └── Workflow Instance
                    │
                    └── Agent Run
                          │
                          └── LangGraph Run
                                │
                                ├── Graph Node
                                ├── Tool Calls
                                ├── ERC Updates
                                ├── RAG Retrieval
                                └── SLM Calls
```

A single conversation may contain multiple workflow instances.

A workflow instance may contain multiple agent runs.

An agent run may contain multiple graph executions or resumptions.

# 6. Request State

Request state exists only for the current API request.

Example:

```yaml
request:
  request_id: req-123
  correlation_id: corr-456
  api_version: v1
  received_at: "..."
  user_message: "What is the affiliation status?"
  conversation_id: conv-123
  session_id: sess-123
```

Request state should not be treated as durable workflow state.

---

# 7. Conversation State

Conversation state represents the user interaction.

Conceptual structure:

```yaml
conversation:
  conversation_id: conv-123
  user_reference: user-123
  session_id: sess-123
  created_at: "..."
  updated_at: "..."
  status: ACTIVE
  active_workflow_instance_id: wf-123
  messages:
    - message_id: msg-1
      role: user
      content: "..."
    - message_id: msg-2
      role: assistant
      content: "..."
```

Conversation state is user-facing continuity.

It is not enterprise business state.

# 15. Workflow Instance State

A workflow instance represents a durable business-oriented AI workflow.

Example:

```yaml
workflow:
  workflow_instance_id: wf-123
  workflow_type: affiliation
  workflow_version: 1.0.0
  status: IN_PROGRESS
  current_state: BUILDING_ERC
  started_at: "..."
  updated_at: "..."
```

The workflow instance is an AI orchestration object.

It is not the enterprise workflow instance.

If the enterprise has a separate workflow identifier, both identifiers must be stored separately.

---

# 16. AI Workflow vs Enterprise Workflow

This distinction is mandatory.

```text
AI Workflow Instance
       │
       │ orchestrates AI interaction
       ▼
Enterprise Workflow Instance
       │
       │ executes business process
       ▼
Enterprise State
```

Example:

```text
AI Workflow ID = ai-wf-123
Enterprise Workflow ID = ent-wf-789
```

The AI workflow references the enterprise workflow.

It does not replace it.

---

# 20. Graph State Design Principle

Do not put every dataset directly into LangGraph state.

Prefer:

```text
Graph State
   ↓
Reference
   ↓
State Store / ERC Store
   ↓
Actual Data
```

This prevents excessive memory consumption and repeated serialization.

# 48. Unknown Transaction State

Example:

```text
AI submits transaction
       ↓
Enterprise accepts
       ↓
Network timeout
       ↓
AI does not know result
```

State:

```text
UNKNOWN
```

Correct behavior:

```text

        ↓
Confirmed SUCCESS → continue
Confirmed FAILURE → handle failure

```

# 50. State Consistency Rules

The following rules are mandatory.

## Rule 1

A child state cannot be `COMPLETED` while its required parent workflow is `CANCELLED`.

## Rule 2

A tool cannot execute when the workflow is unauthorized.

## Rule 3

A workflow cannot be `COMPLETED` while a mandatory operation remains unresolved.

## Rule 4

An ERC marked `PARTIAL` cannot be represented as `COMPLETE`.

## Rule 5

A waiting workflow must persist its resume information.

## Rule 6

An event must be idempotently processed.

## Rule 7

Enterprise state always overrides stale AI state.

Every durable state schema must have a version.

Example:


```text
Old State
   ↓

   ↓
Migration
   ↓
Validation
   ↓

```

# 53. State Persistence

Durable state should be persisted outside the application process.

The persistence architecture must support:

- Pod restart
- Deployment
- Scale-out
- Resume
- Failure recovery
- Long-running workflows
- Event-driven continuation

Resolved: Azure Managed Redis, behind `MemoryStore`/`CacheStore` interfaces regardless of the store — see ADR-D4-10.

---

# 54. State Store Separation

Logical state stores should be separated even when physically hosted on the same platform.

Recommended logical stores:

```text
Conversation Store
Session Store
Workflow/Checkpoint Store
ERC Store
Tool Execution Store
Event Processing Store
Cache
```

This prevents accidental coupling.

# 55. State TTL

Each state category should have an explicit lifecycle.

| State | TTL Strategy |
|---|---|
| Request | Request lifetime |
| Conversation | Business/product retention policy |
| Session | Configurable session TTL |
| Graph checkpoint | Workflow retention |
| ERC | Workflow/data freshness |
| Tool execution | Audit retention |
| Event processing | Operational retention |
| Cache | Short/configurable TTL |
| Evaluation trace | Governance retention |

Retention policies must follow enterprise data/privacy requirements.

# 56. State Security Classification

State must be classified.

Example:

```text
PUBLIC
INTERNAL
CONFIDENTIAL
RESTRICTED
```

Security-sensitive state should be:

- Encrypted
- Access controlled
- Masked in logs
- Restricted from unnecessary SLM exposure

---

# 57. State Serialization

State serialization should be:

- Schema-driven
- Versioned
- JSON-compatible where practical
- Explicitly typed
- Size controlled

Avoid serializing:

- Open network connections
- SDK clients
- Secrets
- Large model objects
- Non-deterministic runtime objects

---

# 58. State and Secrets

Secrets must never be stored in:

- LangGraph state
- Conversation history
- ERC
- Prompts
- Tool results
- Langfuse traces
- User-visible response

Secrets must remain in approved secret management.

```text
BATCH_1
BATCH_2
BATCH_3
...
BATCH_N
 ↓
AGGREGATING
 ↓
ERC
```

Each batch should have independently observable status.

---

# 65. State and Parallel Execution

Parallel branches require aggregation state.

Example:

```text
                    ┌→ Teams ───────┐
                    ├→ Officials ───┤
Context Collection ─┼→ Insurance ───┼→ Aggregation
                    └→ Products ────┘
```

The aggregation node must know:

```text
expected branches
completed branches
failed branches
timed-out branches
mandatory branches
optional branches
```

---

# 66. Partial Completion

Example:

```yaml
parallel_execution:
  expected: 4
  completed: 3
  failed: 1
  mandatory_failed: false
  status: PARTIAL
```

The workflow may continue only if the missing information is not mandatory for the next operation.

---

# 67. State and Enterprise Events

When an event changes enterprise state:

```text
Event Received
 ↓
Validate
 ↓
Identify Workflow
 ↓
Mark Existing ERC STALE
 ↓
Refresh Required Context
 ↓
Update ERC
 ↓
Resume Workflow
```

The AI platform should not simply modify ERC based only on the event if authoritative refresh is required.

---

# 68. State and HIL Resume

Before HIL:

```yaml
workflow:
  status: WAITING_FOR_HUMAN
  resume_node: process_hil_result
```

After event:

```text
Event
 ↓
Workflow Lookup
 ↓
State Validation
 ↓
ERC Refresh
 ↓
Resume Node
```

# 69. State and User Clarification

If required data is missing:

```text
Workflow
 ↓
WAITING_FOR_USER
 ↓
Question
```

User response:

```text
User
 ↓
Conversation
 ↓
Existing Workflow
 ↓
Load checkpoint
 ↓
Resume clarification node
```

The workflow must not restart unnecessarily.

# 70. State and Conversation Summary

Long conversations may require summarization.

The summary should preserve:

- User intent
- Important decisions
- Identifiers
- User-provided facts
- Pending actions
- Workflow state
- Important constraints

Do not summarize away critical enterprise references required for workflow execution.

# 71. State and Memory Boundaries

Memory must be categorized:

```text
Conversation Memory
    ≠
Workflow State
    ≠
ERC
    ≠
Enterprise State
```

A memory retrieval result cannot automatically be considered current operational truth.

# 72. State and Cache Boundaries

Cache:

```text
Temporary reusable state
```

State store:

```text
Durable workflow state
```

Enterprise:

```text
Authoritative business state
```

These boundaries must remain explicit.

# 73. State and SLM

The SLM should receive a projection of state.

It should not receive the entire state store.

```text

 ↓

 ↓

 ↓

```

This reduces:

- Token usage
- Leakage risk
- Latency
- Irrelevant context

# 77. State Recovery Algorithm

Conceptual:

```text
1. Load workflow instance.
2. Validate workflow state version.
3. Load latest graph checkpoint.
4. Validate checkpoint.
5. Load referenced ERC.
6. Validate ERC freshness.
7. Load pending tool/event state.
8. Check transaction idempotency.
9. Determine last safe node.
10. Resume graph.
```

---

# 78. State Recovery Safety

Recovery must not:

- Repeat completed transactions
- Duplicate event processing
- Skip mandatory validation
- Treat stale ERC as current
- Bypass authorization
- Skip guardrails

Recovery is another controlled workflow execution.

---

# 79. State Cancellation

Cancellation may occur due to:

- User cancellation
- Timeout
- Security block
- Administrative cancellation
- Workflow expiration
- Dependency failure

Cancellation state:

```text
ACTIVE
 ↓
CANCELLING
 ↓
CANCELLED
```

Any in-flight external transaction must be checked independently because cancelling an AI workflow does not necessarily cancel an enterprise transaction.

---

# 80. State Expiration

AI workflow expiration should not imply enterprise cancellation.

Example:

```text
AI Workflow
 ↓
EXPIRED
```

Enterprise application may remain:

```text
PENDING
```

A future conversation may create a new AI workflow referencing the same enterprise application.

---

# 81. State Rehydration

A new pod/process must be able to reconstruct:

```text
Conversation
Session
Workflow
Graph checkpoint
ERC reference
Pending actions
Tool status
Event status
```

without depending on local process memory.

---

# 82. State Store Failure

If the durable state store is unavailable:

```text
New Workflow
 ↓
State Store Failure
 ↓
Do not start non-recoverable workflow
 ↓
Safe failure
```

For an active workflow:

```text
State Store Failure
 ↓
Do not execute unsafe transaction
 ↓
Retry/recover
```

The platform must favor recoverability over uncontrolled execution.

---

# 83. State Consistency with Enterprise

The AI runtime should use:

```text
Read → Reason → Act → Confirm → Update State
```

For important operations:

```text
Read authoritative state
 ↓
Reason
 ↓
Execute authorized operation
 ↓
Confirm authoritative result
 ↓
Update AI state/ERC
```

# 86. Optimistic Concurrency

Multiple requests/events may attempt to update the same workflow.

Use:

```text
workflow_id
version
expected_version
new_version
```

Example:

```text
Current Version = 10

Request A expects 10 → updates to 11
Request B expects 10 → rejected/reconciled
```

This prevents lost updates.

---

# 87. State Locking

For critical transitions, the runtime may require:

- Optimistic concurrency
- Distributed lock
- Single-consumer processing
- Idempotency

The selected mechanism depends on the state store and workflow requirements.

# 88. State Race Conditions

Potential race:

```text

      ↓
Workflow Resume

Service Bus Event
      ↓
Workflow Resume
```

Both may attempt the same transition.

The workflow state store must prevent duplicate execution.

# 98. State Model Acceptance Criteria

The implementation is acceptable when:

1. Conversation state is separate from enterprise state.
2. Session state is separate from conversation state.
3. AI workflow state is separate from enterprise workflow state.
4. LangGraph state is durable and recoverable.
5. ERC has explicit lifecycle states.
6. Large collection batches have independent state.
7. Tool calls have explicit lifecycle.
8. RAG calls have explicit lifecycle.
9. SLM calls have explicit lifecycle.
10. HIL has an explicit waiting state.
11. External events can resume workflows.
12. Duplicate events are safely handled.
13. Transaction uncertainty is represented.
14. State schemas are versioned.
15. State transitions are observable.
16. State is recoverable after pod restart.
17. State does not contain secrets.
18. AI state cannot override enterprise truth.
19. State updates support concurrency control.
20. User-facing state is separated from internal runtime state.

---

# 99. Final State Principle

The platform must always distinguish:

```text
WHAT THE USER SAID
        ↓
WHAT AI IS DOING
        ↓
WHAT CONTEXT AI HAS
        ↓
WHAT TOOL AI CALLED
        ↓
WHAT ENTERPRISE ACTUALLY SAID
        ↓
WHAT THE AI WORKFLOW SHOULD DO NEXT
```

The most important rule is:

> **AI state is a coordination mechanism. Enterprise state is the business authority.**
