# 1. Purpose

This document defines the runtime architecture and execution lifecycle of the PFF-FA AI Platform.

It explains exactly how a request travels through the platform from the Chat UI to the final response, including:

- FastAPI
- Request validation
- Claims/context propagation
- Conversation Manager
- Session management
- Supervisor
- Workflow-level Agent
- Agent Harness
- LangGraph
- ERC construction
- Enterprise API tools
- Parallel and sequential execution
- RAG
- SLM
- Guardrails
- Memory
- Cache
- Service Bus event handling
- Durable workflow state
- Error handling
- Observability
- AI evaluation
- Response generation

The purpose of this document is to provide the implementation team with a common runtime execution model.

---

# 2. Runtime Design Principle

The runtime follows:

> **API entry → conversational context → workflow routing → controlled agent execution → context acquisition → ERC → reasoning → controlled action → validation → response**

The SLM is a reasoning/generation component inside the runtime.

It is not the runtime itself.

The runtime is controlled by deterministic application code, LangGraph state, tools, guardrails and enterprise contracts.

Owns AI graph execution/state transitions.

# 5. Request Lifecycle

The standard request lifecycle is:

```text
1. Receive Request
2. Validate Request
3. Extract Claims
4. Create/Load Conversation
5. Load Session
6. Load Existing Workflow
7. Determine Intent
8. Select Workflow Agent
9. Create Agent Run
10. Enter Agent Harness
11. Load Prompt
12. Load Context
13. Execute LangGraph
14. Retrieve Enterprise Context
15. Build/Update ERC
16. Retrieve RAG if required
17. Plan/Reason
18. Execute Tools if required
19. Validate Results
20. Update ERC
21. Generate Response
22. Apply Output Guardrails
23. Persist State
24. Record Observability
25. Return Response
```

# 12. Existing Workflow Detection

The runtime checks whether the conversation already has an active workflow.

```text

 │          │
```

---

# 26. Batch Failure

Example:

```text
Batch 1 SUCCESS
Batch 2 SUCCESS
Batch 3 TIMEOUT
Batch 4 SUCCESS
```

The runtime:

1. Retries according to policy.
2. Records batch failure.
3. Prevents duplicate successful processing.
4. Determines whether the missing batch is critical.
5. Updates ERC completeness.
6. Continues only if safe.
7. Otherwise pauses/fails safely.

# 56. Runtime Retry Hierarchy

Retries must be bounded.

```text
Enterprise API retry
       ↓
Tool retry
       ↓
Graph retry
       ↓
Agent-level recovery
       ↓
Workflow-level recovery
```

Do not multiply retries unintentionally.

For example:

```text
3 API retries × 3 tool retries × 3 graph retries
```

could produce 27 attempts.

Retry budgets must be coordinated.

- Cost/workflow
- Cost/agent
- Cost/conversation
- Model comparison

# 64. Runtime Failure Matrix

| Failure | Runtime Action |
|---|---|
| Invalid request | Reject |
| Unauthorized claims | Reject |
| Ambiguous intent | Clarify |
| API timeout | Retry / partial |
| API unavailable | Degrade / pause |
| Batch failure | Retry / partial |
| ERC incomplete | Continue only if safe |
| RAG unavailable | Continue without RAG if safe |
| SLM timeout | Retry/fallback |
| Tool unauthorized | Block |
| Tool validation failure | Block |
| Guardrail failure | Block/regenerate |
| Service Bus duplicate | Ignore duplicate |
| Service Bus failure | Retry/DLQ |
| Graph failure | Recover/resume |
| Pod restart | Resume checkpoint |
| Cache unavailable | Bypass cache |
| Enterprise transaction timeout | Query status before retry |

# 66. Runtime State Transition Rules

The state transition must be deterministic.

Examples:

```text
API validation failure
→ FAILED

Ambiguous intent
→ NEEDS_CLARIFICATION

HIL required
→ WAITING_FOR_HUMAN

Enterprise async action
→ WAITING_FOR_EXTERNAL_EVENT

Successful graph
→ COMPLETED

Retryable dependency failure
→ RETRYING

Unrecoverable technical failure
→ FAILED
```

---

# 67. Runtime Recovery

Recovery must identify the last safe checkpoint.

```text
Pod Crash
 ↓
Load Workflow State
 ↓
Load Graph Checkpoint
 ↓
Load ERC Reference
 ↓
Validate State
 ↓
Resume
```

The runtime must avoid replaying non-idempotent actions blindly.

# 68. Runtime Deployment Model

The AI runtime may be deployed as one logical application initially:

```text
AI Runtime
 ├── FastAPI
 ├── Conversation
 ├── Supervisor
 ├── Agents
 ├── Harness
 ├── LangGraph
 ├── ERC
 └── Tool Executor
```

Separate deployments may be introduced later for:

- GPU workloads
- High-scale event consumers
- RAG/embedding
- Independent scaling
- Security isolation

Do not split components into microservices without a measurable reason.

# 72. Runtime Design for Affiliation

The Affiliation Agent should be able to:

1. Understand the user request.
2. Identify the club.
3. Load the affiliation application.
4. Determine required context.
5. Retrieve teams.
6. Retrieve officials.
7. Retrieve relevant products/insurance where required.
8. Process large collections using 20-record batches.
9. Build ERC.
10. Retrieve policy knowledge where required.
11. Explain current status.
12. Initiate authorized enterprise operations when required.
13. Wait for enterprise/HIL action.
14. Consume Service Bus events.
15. Refresh ERC.
16. Resume the workflow.
17. Produce a grounded user response.

The enterprise remains authoritative at every business decision point.

# 73. Runtime Non-Goals

The runtime will not:

- Implement enterprise business rules.
- Directly access enterprise databases.
- Implement enterprise scheduling.
- Replace enterprise HIL.
- Replace enterprise workflows.
- Make unauthorized transactions.
- Treat SLM output as enterprise truth.
- Treat RAG output as operational truth.
- Allow unrestricted model-generated HTTP calls.

# 76. Final Runtime Principle

The runtime must preserve this execution hierarchy:

```text
Enterprise Authority
        ↓
Enterprise API / Event
        ↓
AI Context / ERC
        ↓
Controlled AI Reasoning
        ↓
Controlled Tool Execution
        ↓
Enterprise Result
        ↓
AI Explanation
        ↓
User
```

The SLM is a component within this controlled runtime.

It is never the authority for enterprise truth, authorization, business rules or transaction state.
