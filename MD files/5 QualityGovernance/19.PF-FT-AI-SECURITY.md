# 1. Purpose

This document defines the complete security architecture for the PF-FT Enterprise Agentic AI Platform.

Security must protect the complete AI execution chain:

```text

 ↓

 ↓
APIM
 ↓

 ↓
AI Runtime
 ↓

 ↓

 ↓
Agents
 ↓
Harness
 ↓
RAG / Memory / Tools / MCP
 ↓
Enterprise APIs
 ↓
SLM
 ↓

 ↓

```

The security architecture must also cover:

```text
Service Bus
ERC
Portal Links
Configuration
Prompts
Models
Embeddings
Vector Store
Observability
AI Evaluation
CI/CD
Infrastructure
```

# 2. Security Principle

> **AI is an application capability, not a security authority.**

The platform must never allow an LLM, SLM, agent or prompt to independently determine:

```text
Authentication
Authorization
Enterprise permissions
Business policy
Compliance decisions
Security policy
Secret access
Infrastructure access
```

Existing enterprise security controls remain authoritative.

```text
No request is trusted automatically.
No tool is trusted automatically.

No retrieved document is trusted automatically.
```

# 10. Authentication

Authentication remains outside the AI reasoning layer.

The AI platform should consume authenticated identity context provided by the approved enterprise boundary.

The SLM must never authenticate the user.

---

# 11. Authorization

Authorization must remain deterministic.

```text
User Claims
 ↓
APIM / Enterprise Authorization
 ↓
Validated Authorization Context
 ↓
AI Platform
```

The model may reason over authorization context but must not create or modify authorization decisions.

---

# 12. Authorization Context

The AI request context may contain:

```json
{
  "subject": "...",
  "roles": [],
  "permissions": [],
  "organization_ids": [],
  "scopes": []
}
```

Sensitive identity information should be minimized.

---

# 13. Authorization Context Integrity

Claims must:

```text
Originate from trusted authentication infrastructure
Be validated
Be immutable during workflow execution
Be traceable
Not be user-editable
Not be model-editable
```

---

# 15. Authorization Context Boundary

The tool executor should perform the final execution-time authorization validation.

# 176. Final Security Principles

1. **Security is enforced outside the model.**
2. **The model is never an authorization authority.**
3. **APIM and enterprise authorization remain authoritative.**
4. **Every request must have a trusted identity context.**
5. **Authorization context must be immutable during execution.**
6. **Agents operate under least privilege.**
7. **Tools are privileged capabilities and require allowlisting.**
8. **Enterprise APIs are accessed through approved contracts and tools.**
9. **MCP servers and tools are explicitly allowlisted.**
10. **Arbitrary model-generated network requests are prohibited.**
11. **RAG content is data, not instructions.**
12. **Memory is data, not system policy.**
13. **Model output is untrusted until validated.**
14. **PII and secrets require explicit protection.**
15. **Sensitive data sent to external SLM providers must be controlled.**
16. **Self-hosted models require supply-chain and runtime security.**
17. **Configuration is versioned and protected.**
18. **Agents cannot modify their own security configuration.**
19. **Security-critical failures fail closed.**
20. **Retries must never become security bypass mechanisms.**
21. **AI-generated tool calls require deterministic application validation.**
22. **Enterprise deterministic rules remain authoritative.**
23. **RAG ACLs must be enforced before model context construction.**
24. **Cross-user and cross-organization isolation is mandatory.**
25. **Service Bus events must be validated and idempotent.**
26. **Portal links must originate from approved configuration.**
27. **Production systems must not expose unrestricted shell, SQL or network execution.**
28. **Security controls must be observable without leaking sensitive data.**
29. **Security testing must include adversarial AI scenarios.**
30. **AI security evaluation is a release gate, not an optional activity.**
31. **Security configuration changes must be versioned and audited.**
32. **Security incidents must be traceable to the exact platform release and AI configuration.**
33. **Security exceptions must be explicit, approved and time-bound.**
34. **Security must remain active during degraded mode, fallback, rollback and disaster recovery.**
35. **The platform must prioritize confidentiality, integrity, authorization and safety over model convenience.**
