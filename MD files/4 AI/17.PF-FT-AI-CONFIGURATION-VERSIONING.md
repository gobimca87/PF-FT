# 6. Configuration vs Secret

Configuration:

```text
model name
endpoint reference
timeout
retry count
prompt version
API contract version
vector index
temperature
token limit
```

Secret:

```text
API key
client secret
password
certificate private key
access token
connection credential
```

Secrets must not be committed into YAML or source code.

---

# 7. Secret References

Use references:

```yaml
slm:
  api_key_secret_ref: PF_FT_SLM_API_KEY
```

The actual secret is retrieved from the approved secret-management platform.

# 99. Configuration Drift

Configuration drift occurs when runtime configuration differs from the approved release.

Detection:

```text
Approved hash
       vs
Runtime hash
```

Mismatch should trigger investigation.

---

# 100. Configuration Drift Sources

Possible:

```text
Manual change
Environment variable change
Deployment error
Untracked file change
Secret rotation
Provider configuration change
```

Secrets should be treated separately from non-secret configuration when calculating hashes.

        vs

# 176. Final Design Principles

1. **YAML is the primary structured configuration format for the platform.**
2. **Markdown remains the source for detailed architecture and operational documentation.**
3. **Secrets are never stored directly in configuration files.**
4. **Every production AI component has an explicit ID and version.**
5. **Configuration references immutable versions rather than `latest`.**
6. **Environment configuration is separated from base configuration.**
7. **The same tested release artifact should be promoted across environments.**
8. **Runtime configuration is validated before application readiness.**
9. **Invalid mandatory configuration causes fail-fast behavior.**
10. **Configuration dependencies are explicitly validated.**
11. **Prompt, model, agent and workflow versions are correlated.**
12. **RAG, embedding and vector index versions are correlated.**
13. **Tool, API and MCP versions are correlated.**
14. **Guardrail versions are part of the release manifest.**
15. **Configuration changes are evaluated for functional, security and AI-quality impact.**
16. **Production configuration is immutable through normal runtime execution.**
17. **AI agents and SLMs cannot modify their own configuration.**
18. **Every workflow captures a configuration snapshot.**
19. **Every production release has a release manifest.**
20. **Every release is associated with source-control provenance.**
21. **Configuration hashes support drift detection.**
22. **Configuration audit records who, what, when, why and which versions changed.**
23. **Rollback restores a compatible configuration set rather than an isolated component.**
24. **Embedding/vector migrations must preserve compatibility.**
25. **Prompt changes require evaluation and regression testing.**
26. **Model changes require compatibility and AI evaluation.**
27. **Guardrail changes require security evaluation.**
28. **MCP and tool changes require contract and security validation.**
29. **Environment-specific endpoints are configuration bindings, not application logic.**
30. **Production must never depend on undocumented manual configuration.**
31. **Configuration drift must be detectable.**
32. **Configuration must be observable through safe metadata.**
33. **Configuration changes must be traceable in Langfuse/platform telemetry.**
34. **The release manifest is the authoritative description of an AI platform deployment.**
35. **The configuration snapshot is the authoritative configuration context for an individual workflow execution.**
36. **Configuration management is part of AI governance, reliability, security and reproducibility—not merely application settings.**
