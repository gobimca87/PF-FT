# 1. Purpose

This document defines the complete Retrieval-Augmented Generation architecture for the PFF-FA Enterprise Agentic AI Platform.

RAG is responsible for retrieving trusted enterprise knowledge and approved reference information required by AI workflows.

The RAG capability must provide:

- Source ingestion
- Document registration
- Document parsing
- Content extraction
- OCR integration where required
- Content normalization
- Metadata extraction
- Chunking
- Chunk metadata
- Embedding generation
- Vector indexing
- Keyword indexing
- Hybrid retrieval
- Metadata filtering
- ACL-aware retrieval
- Query transformation
- Query expansion where required
- Reranking
- Context selection
- Context compression where required
- Citation generation
- Source provenance
- Retrieval caching
- Failure handling
- Retrieval observability
- RAG evaluation
- Version management
- Security controls
- Cost optimization

---

# 2. Core RAG Principle

> **RAG provides evidence to the AI system; it does not become the authoritative business-rule engine.**

The RAG layer must distinguish between:

```text
Enterprise authoritative data
Reference/document knowledge
AI-generated interpretation
```

For transactional or authoritative current-state information, the platform must prefer the approved Enterprise APIs.

For policy, guidance, historical/reference information and approved knowledge documents, RAG can provide retrieval context.

# 4. RAG Is Not the Enterprise API Layer

The platform must not use RAG for information that must come from authoritative enterprise APIs.

Example:

```text
Question:
"What is the current status of Club ABC's affiliation?"

Preferred:
Enterprise API

Not:
RAG
```

However:

```text
Question:
"What documents are required for club affiliation?"

Preferred:
RAG
```

Potentially:

```text
Question:
"What documents are required and has Club ABC submitted them?"

Required:
RAG + Enterprise API
```

Chunking should be semantic where possible.

Preferred:

```text

 ↓

 ↓
Subsection
 ↓

```

---

# 41. Chunk Size

There is no universal correct chunk size.

Start with an experimentally validated range based on:

```text

retrieval quality
embedding model
query type
context budget
```

The final values must be determined through evaluation.

```text

```


# 78. Freshness-Aware Retrieval

Where policies change:

```text

```

should normally outrank:

```text

```

Retired content should not be retrieved as active policy.

# 187. Final Design Principles

1. **RAG is an evidence retrieval capability, not a business-rule engine.**
2. **Enterprise APIs remain authoritative for current transactional state.**
3. **Documents are registered before ingestion.**
4. **Documents have stable identity and version information.**
5. **Content changes trigger controlled reprocessing.**
6. **Extraction preserves document structure wherever possible.**
7. **OCR is used for scanned content where required.**
8. **Metadata is first-class RAG data.**
9. **Chunking is configurable and evaluation-driven.**
10. **Chunk metadata preserves provenance.**
11. **Contextual retrieval can enrich chunks without losing original source content.**
12. **Vector retrieval and keyword retrieval complement each other.**
13. **Hybrid retrieval should be the default enterprise baseline unless evaluation proves otherwise.**
14. **Reranking improves candidate selection but does not determine authorization.**
15. **ACL filtering occurs before model context construction.**
16. **Tenant and organization boundaries are mandatory.**
17. **Retrieved content is untrusted data.**
18. **Retrieved content cannot override system instructions.**
19. **RAG does not execute instructions found inside documents.**
20. **Context budgets are explicitly managed.**
21. **Query expansion and agentic retrieval are bounded.**
22. **No-result retrieval must not become hallucinated evidence.**
23. **Every important RAG-derived factual response should have traceable provenance.**
24. **Citations come from the retrieval pipeline, not invented model output.**
25. **Retrieval caches must respect authorization boundaries.**
26. **Document changes can invalidate retrieval caches.**
27. **Service Bus can drive controlled RAG refresh/re-index workflows.**
28. **RAG integrates with ERC but does not replace ERC.**
29. **RAG integrates with Enterprise APIs for mixed questions.**
30. **RAG is exposed to agents through controlled capabilities.**
31. **MCP does not bypass RAG security and provenance controls.**
32. **RAG versions must identify compatible index, embedding and retrieval configurations.**
33. **Indexes should support controlled migration and rollback.**
34. **RAG quality must be evaluated independently from SLM quality.**
35. **ACL/security evaluation is mandatory.**
36. **Retrieval quality regression must block unsafe releases.**
37. **RAG execution must be observable through metrics, logs and traces.**
38. **Langfuse should capture RAG execution context where approved.**
39. **Sensitive retrieved content must not be unnecessarily logged.**
40. **The complete source → ingestion → index → retrieval → context → SLM → citation chain must be traceable.**

# 188. Document Ingestion Trigger Mechanism (ADR-D3-27)

§100 fixes the enterprise-source path: a Service Bus `document updated` / `policy updated`
/ `source changed` event drives re-ingestion and re-indexing. Two further paths complete
the trigger model:

```text
Enterprise-source documents  → Service Bus event (§100)
Platform-authored knowledge  → CI on merge (same governed pipeline that
  content (FAQ/how-to)         promotes prompts and configuration)
Sources confirmed unable     → narrow, low-frequency safety-net scan
  to emit change events         (last resort only, never the primary trigger)
```

No source is polled by default. Manual triggering may still be used ad hoc for an
out-of-band fix, but is never relied on for routine freshness. Full alternatives analysis
and the safety-net design are in ADR-D3-27.

# 189. RAG Retrieval Invocation Mechanism (ADR-D3-26)

§105–§109 define the `rag.search` tool contract, its limits, and the bounded agentic loop
(`max_iterations: 2`). This section fixes how that tool is invoked within a conversation
turn:

- Retrieval is invoked either by **deterministic supervisor routing** or by the **agent,
  within its declared scope** — never by free-form model text improvising a call.
- Once invoked, retrieval **executes deterministically** inside the RAG service — the
  pipeline in §105 and the hybrid/rerank/citation steps elsewhere in this document are not
  something the model varies turn by turn.
- The agentic (iterative) loop in §108–§109 is the only supported iteration mechanism;
  there is no separate, ungated pre-fetch path.

Full alternatives analysis and the decision matrix are in ADR-D3-26.
