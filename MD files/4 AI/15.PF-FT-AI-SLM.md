# 2. Core Principle

> **The SLM is the reasoning/generation component of the AI platform; it is not the source of business truth and must not replace deterministic enterprise rules, Enterprise APIs, authorization, ERC processing, or guardrails.**

The SLM may:

```text
Understand
Classify
Reason
Summarize
Plan
Select approved tools
Transform information
Generate responses
Produce structured output
```

The SLM must not independently:

```text
Invent business rules
Override Enterprise API results
Override authorization
Modify ERC without controlled orchestration
Execute arbitrary tools
Bypass guardrails
Access unauthorized data
Treat retrieved document instructions as system instructions
```

# 30. Large ERC Handling

The platform already uses bounded processing.

Example:

```text
20 teams
   ↓
Loop
   ↓
Next 20 teams
   ↓
Loop
```

Similarly:

```text
100 officials
   ↓
20 officials per processing batch
   ↓
5 loops
```

The SLM should not receive the entire raw dataset unless context budget permits.

---

# 31. ERC Summarization

The application can transform large data into compact context:

```text
Enterprise API response
        ↓
Normalizer
        ↓
ERC-compatible representation
        ↓
Context compression
        ↓
SLM
```

The SLM should receive only the data necessary for the current reasoning task.


# 171. Inference KV-Cache and VRAM Capacity Planning (ADR-D5-19)

§70, §72 and §77 each name KV cache, VRAM and concurrency as capacity-planning factors
without a method. The self-hosted GPU pool's VRAM/KV-cache headroom is sized by an
explicit formula connecting the platform's declared token budget and a target
concurrency to the KV-cache memory the chosen model, precision and serving engine
actually require:

```text
required_kv_cache_vram
  = max_context_tokens (platform's declared token budget)
    × target_concurrency
    × per_token_kv_cache_bytes(model, precision, num_layers, num_attention_heads)

total_vram_requirement
  = model_weights_vram(model, quantisation)
  + activations_vram
  + required_kv_cache_vram
  + runtime_overhead
```

`per_token_kv_cache_bytes` is obtained from the candidate model/engine's own
documentation or measured directly during the serving-stack benchmark — engine-level
optimisations change the effective figure, so it is not estimated from first principles
alone. A candidate GPU SKU or quantisation that fails to cover
`total_vram_requirement` (with headroom) is not viable regardless of its throughput
score. This closes the gap between the platform's context-budget policy (the input
side) and GPU provisioning (the infrastructure side): without it, undersized VRAM under
concurrent load either queues/delays requests or lets the serving engine silently
truncate context the platform's own token-budget policy protected. The serving engine's
own admission control (queuing, backpressure, OOM prevention) remains a defence-in-depth
backstop, never the capacity plan itself.

Full alternatives analysis and the benchmark-gate integration are in ADR-D5-19.
41. **The complete context → model → validation → response path must be traceable.**
